## 0.1.2

* Change: Verify page no longer surfaces the consumer's full name. The publicly-reachable verify URL is a tokenised durable medium (Art. 11a(4) Directive 2011/83/EU + GDPR Art. 32(1)(a) pseudonymous access), but a leaked URL previously identified the customer by name in plain text — which is a stricter GDPR Art. 5(1)(c) data-minimisation read than necessary. Aligns with the industry-norm "tokenised receipt" pattern (Stripe `pay.stripe.com/receipts/...`, Square `squareup.com/receipt/...`, Shopify `<store>/orders/<token>`) — receipt page shows only what's needed to verify integrity (receipt number, order number, confirmed-at, refund total, item lines, merchant name, integrity hash) and never the consumer-identifying full name. Customer can still recompute the hash from their email-archived receipt to confirm integrity. Block method `VerifyResult::getConsumerName()` is unchanged (still public, still resolves) so external consumers / extensions remain backward-compatible — only the verify-page template stopped rendering it.
- Fix: Verify page (`/withdraw-contract/verify/index/request_id/<id>/hash/<hash>/`) was rendering unstyled across all themes (Luma, Breeze, Hyva) — looked like a vertically-stacked text dump with default browser typography. Root cause: Lite phase-0.12.6 split its monolithic `_module.less` into per-page bundles (`withdrawal-form.less`, `order-view.less`, `checkout.less`) and stopped loading anything from `default.xml`. The verify page is a Pro module page; nothing in Lite's new bundles touched it. The verify-page LESS partial (`_verify-page.less`) stayed in Lite as orphan code (the 0.12.6 changelog flagged it for "tracked separately" relocation) and was unreferenced from any layout. Verify-page styling worked accidentally only as long as Lite's old global CSS bundle was loaded everywhere.
- Fix files: new `view/frontend/web/css/verify.less` entry-point in this Pro module — self-contained (design tokens copied inline from Lite's `_vars.less` so this Pro module stays independent of Lite's frontend CSS source-tree, which has no shared cross-module @imports). `view/frontend/layout/mageme_eu_withdrawal_verify_index.xml` adds `<css src="MageMe_EUWithdrawalReceiptVerify::css/verify.css"/>` directive — Magento compiles `.less` → `.css` on first request. Lite's orphan `view/frontend/web/css/source/_verify-page.less` removed (in companion 0.12.x bump).

## 0.1.1

- Fix: Verify page (`/withdraw-contract/verify/index/`) always renders monetary amounts in the order's currency rather than defaulting to `'EUR'`. Previously `Block\Withdraw\VerifyResult::formatAmount(string $amount, string $currencyCode = 'EUR')` had a hardcoded default and the template never passed an override, so a $-priced order whose receipt was opened on the verify page rendered as "€XX.XX" — leaving the consumer unable to reconcile against their bank statement. `Controller\Verify\Index` now looks up `sales_order.order_currency_code` by `order.increment_id` (via `OrderRepositoryInterface` + `SearchCriteriaBuilder`) and passes it to the block as `setData('currency_code', ...)`. `VerifyResult::formatAmount()` reads from that data; on lookup failure (controller returned empty) it falls through to `PriceCurrency`'s default which uses the store base currency. The 5 `formatAmount(...)` call sites in `view/frontend/templates/verify/result.phtml` are unchanged — they all use the new currency-aware default.
- Note: ReceiptDto schema is intentionally NOT modified (would invalidate existing content hashes). The currency lookup is a controller-side enrichment only. Receipts written before 0.1.1 verify identically; only the monetary format on the verify page changes.

## 0.1.0

+ New: Initial Pro tier add-on extracted from `MageMe_EUWithdrawal` (Lite) phase-32 split refactor (2026-04-30). Adds forensic-grade durable-medium receipt verification on top of Lite's email receipt: SHA-256 content hash printed in receipt email + public `/withdraw-contract/verify/index/` endpoint for tamper-evidence verification. Pro DI binds `MageMe\EUWithdrawal\Api\Receipt\ContentHasherInterface` to local `ContentHasher` implementation, injects it into Lite's `RequestFinalizer` and `ReceiptSendConsumer` so hash is computed on finalize and validated on send. Lite alone (without this Pro module) writes NULL to `mm_eu_withdrawal_request.content_hash` and the receipt email's integrity-hash table + verify button blocks are hidden via `{{depend content_hash}}` wrappers.
